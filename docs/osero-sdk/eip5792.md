# Execute plans with EIP-5792

Import `@osero/client/eip5792` to submit the pending steps of an `ExecutionPlan` through one
`wallet_sendCalls` request. The wallet must confirm the complete batch atomically.

The adapter also batches plans whose execution requirement is `sequential`. Plan order still
defines call order. A capable wallet executes all pending calls in one atomic bundle.

## Check wallet support

Use `supportsAtomicBatch` to decide whether to show atomic batch UI. The probe returns `false` for
a disconnected wallet, a failed capability request, malformed capabilities, or unsupported atomic
execution. It never throws.

```ts
import { supportsAtomicBatch } from '@osero/client/eip5792';

const canBatch = await supportsAtomicBatch(walletClient);
```

Treat the result as a UI hint. `sendWith` probes again before execution because wallet capabilities
can change after rendering.

## Send a plan

```ts
import { sendWith } from '@osero/client/eip5792';

if (prepared.isErr()) throw prepared.error;

const result = await sendWith(walletClient, prepared.value.plan, {
  confirmations: 2,
  confirmationTimeoutMs: 120_000,
  onProgress(progress) {
    console.log(progress.type);
  },
});

if (result.isErr()) {
  console.error(result.error.code, result.error.toJSON());
} else {
  console.log(result.value.txHash);
  console.log(result.value.transactions);
}
```

One wallet transaction can confirm several logical plan steps. Each `ConfirmedTransaction` keeps
its plan step identity and uses the terminal transaction receipt hash.

## Understand mainnet multi-step execution

Ethereum mainnet sUSDS preparation can produce approve, mint USDS, approve, and deposit steps. The
adapter sends the pending steps as one atomic bundle.

Set `execution: 'atomic-batch'` on `prepareSwap` when the application requires that bundle. For
exact-in USDC to sUSDS that option also sizes the USDS approval and `deposit` as the 1:1 scaled
USDC amount (`raw * 10^12`). The Lite PSM must quote `tin = 0` or prepare fails. A plan marked
`atomic-batch` never falls back to sequential sends.

## Control sequential fallback

Atomic capability discovery can fail or report no support. By default, the adapter then uses the
standard viem executor and sends each pending transaction sequentially.

Set `fallbackToSequential: false` when the application requires one atomic wallet action:

```ts
const result = await sendWith(walletClient, prepared.value.plan, {
  fallbackToSequential: false,
});
```

The adapter returns `UnsupportedCapabilityError` without sending a transaction when fallback is
disabled. A plan whose `requirements.execution` is `atomic-batch` also rejects an unsupported
wallet and never falls back.

## Handle failures and progress

A failed batch is classified, never reported as an unexpected error:

- `wallet_sendCalls` rejected by the user (code `4001` or `5750`) returns `CancelError`. An
  unauthorized account (code `4100`) returns `SigningError`. A wallet that refuses atomic execution
  (code `5760`) is handled like a wallet without atomic support: sequential fallback, or
  `UnsupportedCapabilityError` when fallback is not allowed. Any other submission failure returns
  `BroadcastError`.
- Once the wallet accepts the batch, a status wait that fails or times out returns
  `ConfirmationError`. So does a malformed or non-atomic status. The message names the batch ID.
  The batch may still confirm, so check its status before sending anything again.
- A batch that reverted as a whole returns `TransactionError` with the batch's transaction hash.
- A partial revert returns `ConfirmationError`. The adapter requires atomic execution, so a wallet
  should never report one; if it does, some calls may be on chain and nothing should be resent
  before checking.

`execution.completed` on these errors lists only steps confirmed before the batch, such as a
resumed prefix. A batch the adapter accepts as confirmed confirmed every pending step. Once the wallet has accepted a
batch, `execution.batchId` carries its identifier, so the batch can be looked up in the wallet after
an ambiguous failure.

Progress events are emitted as facts become known: `preflight-complete` and `step-started` when the
wallet accepts the batch, `step-submitted` when the wallet reports the batch's transaction hash, and
`step-confirmed` and `plan-completed` only after confirmation. A batch ID is not a transaction hash,
so a batch whose status wait times out has emitted no `step-submitted` event.

The [adapter behaviour contract](./adapters.md) lists every stage, default, and error mapping.
